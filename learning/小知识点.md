# ThreadLocal 详解

## 一、ThreadLocal 是什么

ThreadLocal 是 Java 提供的一个线程局部变量类，它为每个使用该变量的线程提供独立的变量副本。

### 核心特性

- **线程隔离**：每个线程都有自己的独立副本，互不干扰
- **线程安全**：无需加锁即可实现线程安全
- **内存泄漏风险**：使用不当可能导致内存泄漏

---

## 二、项目中的使用场景

### 2.1 UserHolder 类

```java
package com.hmdp.utils;

import com.hmdp.dto.UserDTO;

public class UserHolder {
    // 创建 ThreadLocal 实例，泛型为 UserDTO，用于存储当前线程的用户信息
    private static final ThreadLocal<UserDTO> tl = new ThreadLocal<>();

    public static void saveUser(UserDTO user) {
        tl.set(user);
    }

    public static UserDTO getUser() {
        return tl.get();
    }
    
    public static void removeUser() {
        tl.remove();
    }
}
```

### 2.2 LoginInterceptor 类

```java
package com.hmdp.utils;

import com.hmdp.dto.UserDTO;
import org.springframework.web.servlet.HandlerInterceptor;

import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;
import javax.servlet.http.HttpSession;

public class LoginInterceptor implements HandlerInterceptor {

    /**
     * 请求处理前的拦截方法
     * 执行时机：在 Controller 方法执行之前
     * 返回值：true 表示放行，false 表示拦截
     */
    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
        HttpSession session = request.getSession();
        Object user = session.getAttribute("user");
        if (user == null) {
            response.setStatus(401);
            return false;
        }
        UserHolder.saveUser((UserDTO) user);
        return true;
    }

    /**
     * 请求处理完成后的回调方法
     * 执行时机：在视图渲染完成后（无论请求是否成功）
     * 执行条件：preHandle 返回 true
     * @param ex 处理过程中发生的异常，如果没有异常则为null
     */
    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler, Exception ex) throws Exception {
        // 移除当前线程中保存的用户信息，防止内存泄漏
        // 重要：Web 容器（如 Tomcat）使用线程池处理请求，线程会被复用
        //      如果不清理 ThreadLocal，下一个请求可能获取到上一个请求的用户信息，
        //      造成数据混乱，同时还会导致内存泄漏（用户对象无法被 GC 回收）
        UserHolder.removeUser();
    }
}
```

## 三、ThreadLocal 底层原理

### 3.1 数据结构

```
Thread (线程)
    └── ThreadLocalMap (每个线程独有)
            ├── Entry1 (key = ThreadLocal实例A, value = 数据A)
            ├── Entry2 (key = ThreadLocal实例B, value = 数据B)
            └── ...
```

### 3.2 核心源码解析

```java
// Thread 类中的成员变量
class Thread {
    // 每个线程维护自己的 ThreadLocalMap
    ThreadLocal.ThreadLocalMap threadLocals = null;
}

// ThreadLocal 类
public class ThreadLocal<T> {
    // 存储数据：获取当前线程的 ThreadLocalMap，并以 this 为 key 存储数据
    public void set(T value) {
        Thread t = Thread.currentThread();  // 获取当前线程
        ThreadLocalMap map = t.threadLocals;  // 获取线程的 ThreadLocalMap
        if (map != null) {
            map.set(this, value);  // 以 this（ThreadLocal实例）为 key 存储数据
        } else {
            createMap(t, value);  // 首次使用时创建 ThreadLocalMap
        }
    }

    // 获取数据：从当前线程的 ThreadLocalMap 中获取以 this 为 key 的值
    public T get() {
        Thread t = Thread.currentThread();
        ThreadLocalMap map = t.threadLocals;
        if (map != null) {
            ThreadLocalMap.Entry e = map.getEntry(this);
            if (e != null) {
                return (T) e.value;
            }
        }
        return setInitialValue();  // 如果不存在，返回初始值（默认为 null）
    }

    // 移除数据：从当前线程的 ThreadLocalMap 中删除以 this 为 key 的条目
    public void remove() {
        Thread t = Thread.currentThread();
        ThreadLocalMap map = t.threadLocals;
        if (map != null) {
            map.remove(this);
        }
    }
}
```

### 3.3 ThreadLocalMap 的 Entry 是弱引用

```java
static class Entry extends WeakReference<ThreadLocal<?>> {
    Object value;
    Entry(ThreadLocal<?> k, Object v) {
        super(k);  // key 是弱引用，指向 ThreadLocal 实例
        value = v; // value 是强引用
    }
}
```

**弱引用的作用**：
- key（ThreadLocal 实例）是弱引用，当 ThreadLocal 实例没有外部强引用时，可被 GC 回收
- value 是强引用，如果 key 被回收但 value 还在，就会造成内存泄漏
- **解决方法**：调用 `remove()` 方法清理整个 Entry

## 四、为什么在拦截器中使用 ThreadLocal

### 4.1 传统方式的问题

```java
// 不使用 ThreadLocal：每个方法都需要传递 request 参数
@GetMapping("/me")
public Result me(HttpServletRequest request) {
    HttpSession session = request.getSession();
    UserDTO user = (UserDTO) session.getAttribute("user");
    return Result.ok(user);
}

@GetMapping("/orders")
public Result myOrders(HttpServletRequest request) {
    HttpSession session = request.getSession();
    UserDTO user = (UserDTO) session.getAttribute("user");
    // 查询该用户的订单...
}
```

**问题**：
- 每个方法都需要 `HttpServletRequest` 参数
- 代码重复，冗余

### 4.2 使用 ThreadLocal 的优势

```java
// 使用 ThreadLocal：直接获取用户信息，无需传参
@GetMapping("/me")
public Result me() {
    UserDTO user = UserHolder.getUser();  // 直接获取，简洁明了
    return Result.ok(user);
}

@GetMapping("/orders")
public Result myOrders() {
    UserDTO user = UserHolder.getUser();
    // 查询该用户的订单...
}
```

**优势**：
- 代码简洁，无需传递参数
- 解耦：业务代码不需要感知 request/session
- 线程安全：每个请求在独立线程中处理，互不干扰

## 五、ThreadLocal 的使用流程

### 5.1 完整的请求处理流程

```
┌─────────────────────────────────────────────────────────────┐
│                    请求到达                                  │
└─────────────────────┬───────────────────────────────────────┘
                      │
                      ▼
┌─────────────────────────────────────────────────────────────┐
│            LoginInterceptor.preHandle()                      │
│  1. 从 session 获取用户信息                                   │
│  2. 调用 UserHolder.saveUser(user)                          │
│     → ThreadLocal.set(user)                                  │
│     → 数据存入当前线程的 ThreadLocalMap                      │
└─────────────────────┬───────────────────────────────────────┘
                      │
                      ▼
┌─────────────────────────────────────────────────────────────┐
│              Controller 业务方法执行                          │
│  - UserHolder.getUser() → 获取当前线程的用户信息              │
│  - 业务逻辑处理                                              │
└─────────────────────┬───────────────────────────────────────┘
                      │
                      ▼
┌─────────────────────────────────────────────────────────────┐
│          LoginInterceptor.afterCompletion()                  │
│  调用 UserHolder.removeUser()                               │
│  → ThreadLocal.remove()                                     │
│  → 清理当前线程的 ThreadLocalMap 中的数据                     │
│  → 防止内存泄漏和数据污染                                     │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 线程池场景下的重要性

```
线程池：[Thread-1] [Thread-2] [Thread-3]

请求1 → Thread-1: ThreadLocal 中存储 UserA
          ↓
       处理完成，调用 remove() 清理
          ↓
       Thread-1 回到线程池

请求2 → Thread-1: ThreadLocal 中存储 UserB
          ↓
       处理完成，调用 remove() 清理
          ↓
       Thread-1 回到线程池

如果不调用 remove()：
请求1 → Thread-1: ThreadLocal 中存储 UserA
          ↓
       【未清理】
          ↓
请求2 → Thread-1: ThreadLocal 中仍然是 UserA！
          ↓
       数据污染：请求2误认为是 UserA 在操作
```

## 六、ThreadLocal 的常见问题

### 6.1 内存泄漏

**原因**：
- ThreadLocalMap 的 Entry 中，key 是弱引用，value 是强引用
- ThreadLocal 实例被回收后，key 变为 null
- 但 value 仍然存在，且无法被访问（因为 key 是 null）
- 如果线程长期存活（如线程池），value 不会被 GC 回收

**解决**：
- 务必调用 `remove()` 方法清理
- 在拦截器的 `afterCompletion()` 中清理是一个很好的实践

### 6.2 父子线程数据传递

ThreadLocal 默认不能在父子线程之间传递数据：

```java
// 主线程
ThreadLocal<String> tl = new ThreadLocal<>();
tl.set("主线程数据");

// 子线程
new Thread(() -> {
    System.out.println(tl.get());  // 输出 null，获取不到主线程的数据
}).start();
```

**解决方法**：使用 `InheritableThreadLocal`

```java
InheritableThreadLocal<String> tl = new InheritableThreadLocal<>();
tl.set("主线程数据");

new Thread(() -> {
    System.out.println(tl.get());  // 输出 "主线程数据"
}).start();
```

## 七、总结

### 7.1 ThreadLocal 的使用场景

| 场景 | 说明 |
|------|------|
| 用户上下文传递 | 本项目：在拦截器中保存用户信息，业务代码直接获取 |
| 数据库连接管理 | 每个线程使用独立的数据库连接 |
| 日期格式化 | SimpleDateFormat 不是线程安全的，可用 ThreadLocal 包装 |
| 事务管理 | 每个线程管理自己的事务上下文 |

### 7.2 最佳实践

1. **务必清理**：使用后必须调用 `remove()`，防止内存泄漏
2. **避免存储大对象**：ThreadLocal 存储的对象会随线程生命周期存在
3. **注意线程池**：线程池中的线程会复用，必须清理数据
4. **使用 static final**：ThreadLocal 实例通常声明为 `static final`

# Spring 拦截器中的依赖注入详解

## 一、问题背景

在项目中，我们有两种不同的依赖注入方式：

### 1.1 LoginInterceptor：构造函数注入

```java
package com.hmdp.utils;

import com.hmdp.dto.UserDTO;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.web.servlet.HandlerInterceptor;

public class LoginInterceptor implements HandlerInterceptor {

    private StringRedisTemplate stringRedisTemplate;

    /**
     * 构造函数注入 StringRedisTemplate
     * 为什么不能用 @Autowired 直接注入？因为 LoginInterceptor 不是 Spring 管理的 Bean！
     */
    public LoginInterceptor(StringRedisTemplate stringRedisTemplate) {
        this.stringRedisTemplate = stringRedisTemplate;
    }

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        // 使用 stringRedisTemplate...
        return true;
    }
}
```

### 1.2 MvcConfig：字段注入 + 手动创建

```java
package com.hmdp.config;

import com.hmdp.utils.LoginInterceptor;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.web.servlet.config.annotation.InterceptorRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

import javax.annotation.Resource;

@Configuration  // 【关键】这是一个配置类，会被 Spring 管理
public class MvcConfig implements WebMvcConfigurer {

    @Resource  // Spring 依赖注入，自动注入 StringRedisTemplate Bean
    private StringRedisTemplate stringRedisTemplate;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        // 【关键】手动创建 LoginInterceptor 实例，并传入依赖
        registry.addInterceptor(new LoginInterceptor(stringRedisTemplate))
                .excludePathPatterns("/shop/**", "/user/login");
    }
}
```

## 二、核心问题：为什么不能在 LoginInterceptor 中直接依赖注入？

### 2.1 什么是 Spring 配置类？

```java
@Configuration  // 【重要】这个注解让 Spring 识别该类
public class MvcConfig {
    // ...
}
```

**配置类的特点**：
1. 带有 `@Configuration` 注解
2. 被 Spring 容器管理（成为一个 Bean）
3. 可以使用依赖注入注解（`@Autowired`、`@Resource` 等）
4. 可以定义和注册其他 Bean

### 2.2 什么是 Spring Bean？

```java
// Spring Bean 的定义方式
@Configuration
public class AppConfig {
    @Bean  // 【重要】告诉 Spring 这个方法返回的对象要被 Spring 管理
    public StringRedisTemplate stringRedisTemplate() {
        return new StringRedisTemplate();
    }
}
```

**Spring Bean 的特点**：
- 由 Spring 容器创建和管理的对象
- Spring 负责其生命周期（创建、初始化、销毁）
- 支持依赖注入
- 可以使用 AOP 等高级特性

### 3.2 依赖注入的底层实现（源码级别）

```java
// Spring 框架中处理 @Autowired 的核心代码（简化版）
public class AutowiredAnnotationBeanPostProcessor implements BeanPostProcessor {

    @Override
    public Object postProcessProperties(PropertyValues pvs, Object bean, String beanName) {
        // 1. 查找类中所有需要注入的字段（带 @Autowired、@Resource）
        InjectionMetadata metadata = findAutowiringMetadata(bean.getClass());

        try {
            // 2. 遍历所有需要注入的字段
            metadata.inject(bean, beanName, pvs);

            // 3. 注入逻辑：从 Spring 容器中获取对应的 Bean，然后通过反射设置字段值
            Field field = (Field) element.getMember();
            field.setAccessible(true);  // 打破私有访问限制
            field.set(bean, value);      // 通过反射设置字段值
        } catch (Throwable ex) {
            throw new BeanCreationException(beanName, "Injection of autowired dependencies failed", ex);
        }

        return bean;
    }
}
```

**关键点**：
1. 只有 Spring 管理的 Bean 才会经过 `BeanPostProcessor` 的处理
2. `AutowiredAnnotationBeanPostProcessor` 负责处理 `@Autowired` 注解
3. 通过反射机制将依赖注入到字段中
4. **非 Bean 对象不经过这个流程**

## 四、为什么拦截器需要这样处理？

### 4.1 Spring MVC 中拦截器的注册方式

```java
// WebMvcConfigurer 接口定义了扩展 Spring MVC 的方法
public interface WebMvcConfigurer {
    /**
     * 注册拦截器
     * @param registry 拦截器注册器
     */
    default void addInterceptors(InterceptorRegistry registry) {
    }
}
```

**关键问题**：Spring MVC 的拦截器注册机制允许开发者**手动创建拦截器实例**，而不是强制要求拦截器必须是 Spring Bean。

### 4.2 拦截器的两种注册方式对比

#### 方式一：手动创建拦截器实例（本项目使用）

```java
@Configuration
public class MvcConfig implements WebMvcConfigurer {

    @Resource
    private StringRedisTemplate stringRedisTemplate;  // Spring 注入

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        // 手动创建拦截器，传入依赖
        LoginInterceptor interceptor = new LoginInterceptor(stringRedisTemplate);
        registry.addInterceptor(interceptor);
    }
}
```

#### 方式二：将拦截器也注册为 Bean

```java
// 1. 让 LoginInterceptor 成为 Spring Bean
@Component  // 添加 @Component 注解
public class LoginInterceptor implements HandlerInterceptor {

    @Autowired  // 可以使用依赖注入
    private StringRedisTemplate stringRedisTemplate;

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        return true;
    }
}

// 2. 在配置类中注入拦截器
@Configuration
public class MvcConfig implements WebMvcConfigurer {

    @Autowired
    private LoginInterceptor loginInterceptor;  // 注入拦截器 Bean

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(loginInterceptor);  // 直接使用注入的拦截器
    }
}
```

**两种方式的对比**：

| 特性 | 方式一（手动创建） | 方式二（Bean 注册） |
|------|-------------------|-------------------|
| 拦截器是否为 Bean | 否 | 是 |
| 能否使用 `@Autowired` | 不能 | 能 |
| 构造函数注入 | ✅ 支持 | ❌ 不需要 |
| 适用场景 | 简单拦截器 | 需要多依赖注入的拦截器 |

## 六、Spring 依赖注入的三种方式

### 6.1 构造函数注入（推荐）

```java
@Service
public class UserService {

    private final UserRepository userRepository;

    /**
     * 构造函数注入
     * 优点：
     * 1. 明确的依赖关系
     * 2. 保证对象不可变（final 字段）
     * 3. 保证依赖不为 null
     * 4. 便于单元测试
     */
    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }
}
```

### 6.2 Setter 注入

```java
@Service
public class UserService {

    private UserRepository userRepository;

    /**
     * Setter 注入
     * 优点：
     * 1. 灵活：依赖可以随时改变
     * 缺点：
     * 1. 依赖可能为 null
     * 2. 不是不可变的
     */
    @Autowired
    public void setUserRepository(UserRepository userRepository) {
        this.userRepository = userRepository;
    }
}
```

### 6.3 字段注入

```java
@Service
public class UserService {

    /**
     * 字段注入
     * 优点：
     * 1. 代码简洁
     * 缺点：
     * 1. 依赖可能为 null
     * 2. 不能使用 final
     * 3. 不利于单元测试
     * 4. 反射破坏封装
     */
    @Autowired
    private UserRepository userRepository;
}
```

**推荐顺序**：构造函数注入 > Setter 注入 > 字段注入

```java
// WebMvcConfigurerComposite：Spring 内部类，聚合多个 WebMvcConfigurer
class WebMvcConfigurerComposite implements WebMvcConfigurer {

    private final List<WebMvcConfigurer> delegates;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        // 遍历所有的 WebMvcConfigurer（包括我们的 MvcConfig）
        for (WebMvcConfigurer delegate : this.delegates) {
            delegate.addInterceptors(registry);
        }
    }
}

// RequestMappingHandlerMapping：注册拦截器到请求处理流程
public class RequestMappingHandlerMapping extends AbstractHandlerMethodMapping<MethodInfo> {

    protected void initInterceptors() {
        // 获取所有注册的拦截器
        Map<String, HandlerInterceptor> interceptors = registry.getInterceptors();

        // 将拦截器添加到处理器映射中
        for (Map.Entry<String, HandlerInterceptor> entry : interceptors.entrySet()) {
            String name = entry.getKey();
            HandlerInterceptor interceptor = entry.getValue();
            // 拦截器将被用于后续的请求处理
            adaptInterceptor(interceptor);
        }
    }
}
```

## 八、总结

### 8.1 核心要点

| 概念 | 说明 |
|------|------|
| **配置类** | 带有 `@Configuration` 注解，被 Spring 容器管理 |
| **Bean** | 由 Spring 容器创建和管理的对象 |
| **依赖注入** | Spring 自动将依赖注入到 Bean 中 |
| **非 Bean 对象** | 手动创建的对象，Spring 不管理，无法自动依赖注入 |

### 8.2 为什么 LoginInterceptor 不能直接依赖注入？

1. **不是 Bean**：`LoginInterceptor` 没有 `@Component` 等注解，不是 Spring 管理的对象
2. **容器边界**：Spring 只对自己管理的对象进行依赖注入
3. **设计原则**：Spring 不"接管"手动创建的对象，保持清晰的边界

### 8.3 解决方案

```java
// 在配置类中：
// 1. 先获取需要的依赖（Spring 注入）
@Resource
private StringRedisTemplate stringRedisTemplate;

// 2. 手动创建拦截器时传入依赖
new LoginInterceptor(stringRedisTemplate)
```
